## 一、现象

- 双击 `lims-desktop.exe`：窗口标题正常（实训室信息管理系统），内容区**纯白**；
- 或进程留在后台、再双击无任何反应（它占着单实例端口 51739，后续启动会静默退出）；
- 新版已加看门狗：超时后弹中文错误框并写日志，退出码 **2**。

## 二、根因

每一个**新启动**的 WebView2 浏览器进程都在早期初始化时崩溃：

```
Faulting application name: msedgewebview2.exe
Faulting module name:      msedge_elf.dll          (Chromium 的早期加载框架)
Exception code:            0x80000003              (STATUS_BREAKPOINT)
Faulting module path:      C:\Program Files (x86)\Microsoft\EdgeWebView\Application\154.0.4258.37\msedge_elf.dll
```

崩溃只发生在这份**机器级**运行时目录里，而它的安装器上次是**带错误结束**的：

| 项 | 值 |
| --- | --- |
| HKLM ClientState `pv` | `154.0.4258.37` |
| `LastInstallerError` | `2` |
| `updatecount` | `40` |
| 另一份运行时 | 用户级 `%LOCALAPPDATA%\Microsoft\EdgeWebView\Application\154.0.4258.48`（由 EdgeUpdate 的 force-install 新增） |

已经排除的方向（都实测过，不必再试）：

- 前端资源没嵌进 exe —— 已修复，`findstr /M /C:"assets/" lims-desktop.exe` 有命中；
- `--disable-features` 参数（三种变体表现完全相同）；
- 应用数据目录权限（ACL 干净，用户 FullControl）；
- 兼容性垫片 / `AppInit_DLLs` / IFEO 逐进程拦截 / 逐应用漏洞利用防护 / Smart App Control / DeviceGuard；
- 环境变量：**没有缺失关键项**（`SystemRoot`、`LOCALAPPDATA` 等是登录时注入的会话变量，本就不在 Machine/User 注册表里）；WebView2 也不依赖任何环境变量。

对照事实：同版本 **Edge 本体正常**（它用自己的 `Program Files (x86)\Microsoft\Edge\Application\` 副本）；
09/29 之前启动、一直在跑的 WebView2 宿主（Windows 搜索、GameViewer）也正常（文件早已映射进内存）。

> ### 2026-09-30 22:24 追加：真正的最后一环是"数据目录可写性"
>
> 用可逆对照实验（把用户级运行时目录临时改名）证明：**两份运行时都能正常工作**
> （两次运行都是 6 个浏览器子进程、0 崩溃、界面正常）。
> 真正决定成败的是——**运行进程能否写自己的 WebView2 数据目录**：
>
> | 启动方式 | 数据目录可写 | 结果 |
> | --- | --- | --- |
> | 正常会话（资源管理器 / Win+R / 不受限） | 是 | 界面正常 |
> | 被文件级限制的进程（如从沙箱化的工作区界面里双击） | 否 | AppData 与临时目录都写不进 → 浏览器进程崩在 `msedge.dll`（`0x80000003`）→ 白屏 |
>
> 因此代码里把数据目录候选改成**三级降级**（`lib.rs` 的 `webview_data_dir_candidates`）：
>
> 1. `%LOCALAPPDATA%\<identifier>\WebView2`（正常安装）
> 2. **`<exe 同级>\lims-webview2-data`**（便携部署；也是进程被限制时唯一还可能可写的位置）
> 3. `%TEMP%\lims-desktop-webview2`
>
> 每一级都必须**真写一个探针文件**确认可写才采用（只看 `create_dir_all` 不够：
> 目录已存在时会假成功，那种目录交给 WebView2 必崩）。
> 启动日志同样按这三级找落点，所以哪怕系统目录写不了，日志仍会落在 exe 同级，
> 现场直接看 `startup.log` 就能知道它选了哪个目录、卡在哪一步。

## 五、桌面端新增的自检能力（本轮加的，已实测）

| 能力 | 行为 |
| --- | --- |
| 启动看门狗 | WebView2 在 `LIMS_WEBVIEW_TIMEOUT_MS`（默认 30 秒）内未就绪 → 写日志 + 弹中文错误框 + 以退出码 2 结束 |

## 六、对齐微软官方方案（2026-09-30 23:20 完成）

按微软官方文档补齐了三处，并**实测通过**：

| 补齐项 | 实现 | 实测证据 |
| --- | --- | --- |
| **运行期失败监听** | 接官方 `CoreWebView2.ProcessFailed`（`webview_health.rs`）。渲染进程崩 → 记日志 + 自动重载（同会话≤3 次）；浏览器进程退出 → 弹框 + 退出码 2；无响应 → 只记一次日志（官方会重复上报） | 杀渲染进程：日志 `kind=1` → `已尝试重载页面…`，应用存活；杀浏览器进程：日志 `kind=0` → `判定不可自愈`，弹框 + **退出码 2** |
| **运行时版本探测** | 启动时读 `pv`（HKLM `WOW6432Node` 与 HKCU 各一处）写进日志；未安装时错误框直接说明"未安装 WebView2 运行时" | 日志出现 `WebView2 运行时版本 154.0.4258.48` |
| **单实例换内核对象** | 命名互斥体 `Local\com.sxsinfo.lims.desktop.single-instance` + 命名事件 `…activate`，**不再占 TCP 端口** | 第二次启动**退出码 0**、首个实例继续运行 |

**关于安装期的运行时依赖**：查了 tauri 生成的安装脚本后确认，**NSIS 与 MSI 都已内建**"读 `pv` → 缺则安装"的官方流程
（NSIS：`Section WebView2` + `INSTALLWEBVIEW2MODE`；WiX：`WVRTINSTALLED` 注册表探测 + `DownloadAndInvokeBootstrapper` 自定义动作）。
所以**不要自己写 NSIS 钩子**去重复这件事（我原先加过一个，确认重复后已删除）。
只需要在 `tauri.conf.json` 里按部署场景选模式：

- `downloadBootstrapper`（默认）：安装时联网下载官方分发器，安装包最小（本工程当前用的就是它）；
- `embedBootstrapper`：把分发器打进安装包（+约 1.8 MB，仍要联网）；
- `offlineInstaller`：把离线安装器打进包（+约 127 MB，**完全离线部署用这个**）；
- `fixedRuntime`：把指定版本运行时打进包（+约 180 MB，版本完全自控）；
- `skip`：完全不检测（不推荐）。
